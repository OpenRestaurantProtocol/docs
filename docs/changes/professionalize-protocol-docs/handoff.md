# Handoff: Profissionalizar a documentação do Open Restaurant Protocol

## Grilling walk trace
- destination: Deixar a documentação do ORP profissional como a de protocolos genéricos (ex. Model Context Protocol), com versionamento real (v1, v2...), uma página de Discovery padronizando OAuth+MCP, e um template de Contratos de Dados por domínio.
- walk turns: 4
- decisions resolved:
  - Local dos artefatos de planejamento: criar `docs/changes/` e excluir via `exclude_docs` do mkdocs.yml (consistente com o padrão já usado para `diagrams/oauth/*.json`/`*.mjs`).
  - Mecanismo de versionamento: plugin `mike` (builds versionados reais + seletor nativo no tema Material), não uma página de changelog nem diretórios manuais.
  - Escopo de "alta descoberta": consolidar numa página `discovery.md` dedicada o conteúdo de RFC 8414/RFC 9728/DCR já escrito e espalhado em `oauth-requirements.md`/`mcp-oauth.md`, sem duplicar.
  - Contratos de Dados: página de template genérico (campos, exemplo de payload, nota de versionamento), sem inventar domínios reais, marcada "em desenvolvimento" — porque não há artefato-fonte de domínios reais (diferente do OAuth, que veio dos docs do toqan).
  - Navegação: 4 abas de topo — Especificação, Autenticação (com Discovery dentro), Contratos de Dados, Integrações. Discovery fica dentro de Autenticação por ser mecânica OAuth/resource-metadata, não uma aba isolada.
  - Referência de estilo: site oficial do Model Context Protocol (Overview/Key Details, cards "Learn More", versão no cabeçalho) — coerente por o protocolo ser construído explicitamente sobre MCP.
  - "Início" se funde na nova aba "Especificação" (mesmo arquivo `index.md`, conteúdo reestruturado), em vez de manter duas abas separadas na entrada do nav.
  - Cadência de validação: `per-step`, dado o risco real de regressão no domínio customizado durante a migração do gh-pages.
- open points: nenhum — todas as decisões do design tree foram resolvidas e a execução foi confirmada pelo usuário (R7).
- terms clarified: "alta descoberta" (R4) — esclarecido como a consolidação dos mecanismos de descoberta automática RFC 8414 (Authorization Server Metadata) + RFC 9728 (Protected Resource Metadata) + RFC 7591 (Dynamic Client Registration) já parcialmente documentados, numa página dedicada.
- contradictions surfaced:
  - A listagem inicial da branch `gh-pages` via `scout` (`git ls-tree` sem fetch prévio) NÃO mostrava o arquivo `CNAME`, sugerindo uma possível perda do domínio customizado. Um `git fetch origin gh-pages` fresco via `worker` contradisse essa leitura: o `CNAME` existe e contém `openrestaurantprotocol.org`. A causa raiz foi uma referência local `origin/gh-pages` desatualizada no scout (que não tem permissão de `git fetch`), não uma perda real do CNAME.

## Research findings
- `jimporter/mike` README (https://raw.githubusercontent.com/jimporter/mike/master/README.md): config do plugin em `mkdocs.yml` (`plugins: - mike: {...}` com defaults incluindo `version_selector: true`), instalação (`pip install mike`), comandos `mike deploy [version] [alias]...` e `mike set-default [identifier]`, seção "## How It Works" (deploy de uma versão sobrescreve só aquela versão; outras versões "remain untouched"), seção "## Before Using mike" (recomenda `mike delete --all` para limpeza inicial — EVITADO neste plano por apagar o CNAME junto), seção "## Deploying via CI" (clone shallow em CI precisa de `git fetch origin gh-pages --depth=1` antes do mike rodar, e configuração de git user via `git config user.name`/`user.email`), e seção dedicada "## `CNAME` (and Other Special Files)" — mike não tem tratamento especial para CNAME, deve ser commitado manualmente na raiz da branch.
- mkdocs-material — Setting up versioning (https://squidfunk.github.io/mkdocs-material/setup/setting-up-versioning/): bloco `extra: version: provider: mike` necessário no `mkdocs.yml` para o seletor de versão aparecer no tema; exemplos de comando `mike deploy --push --update-aliases 0.1 latest` e `mike set-default --push latest`.
- Site oficial do Model Context Protocol (https://modelcontextprotocol.io/specification/2025-06-18): seletor de versão no cabeçalho (rótulo "Version 2025-06-18", dropdown listando "Version 2026-07-28 (latest)", "Version 2025-11-25", "Version 2025-06-18", "Version 2025-03-26", "Version 2024-11-05", e um item "Draft"); seções de topo "Overview", "Key Details", "Security and Trust & Safety", "Learn More".

## Decisions
- Versionamento via `mike` (não changelog manual nem diretórios manuais): porque é a ferramenta dedicada e madura pra exatamente esse caso de uso, com integração nativa ao tema mkdocs-material já em uso (descartada: página única de changelog — mais simples, mas impede navegar versões antigas depois que uma nova é publicada; descartada: diretórios manuais sem plugin — duplicação de conteúdo e manutenção manual de nav a cada versão).
- Discovery consolidado numa página nova, sem duplicar: porque o conteúdo técnico de RFC 8414/RFC 9728/DCR já está integralmente escrito em `oauth-requirements.md`/`mcp-oauth.md` — o pedido do usuário leu como "dar um lar próprio a esse conteúdo", não criar conteúdo novo do zero (descartada: página nova só sobre configuração de cliente MCP, mantendo as páginas de OAuth intocadas — escopo mais estreito, mas não endereça o pedido de "padronização... para alta descoberta" como pilar próprio).
- Contratos de Dados como template genérico, sem domínios inventados: porque não existe artefato-fonte de domínios reais (diferente do OAuth, que veio dos docs do toqan) — inventar nomes de domínio criaria conteúdo não solicitado e potencialmente incorreto (descartada: esqueleto com subpáginas stub por domínio inferido das tools já citadas em `oauth.md` — mais estrutura, mas inventa nomes de domínio não confirmados pelo usuário).
- Discovery dentro da aba Autenticação, não como aba isolada: porque Discovery é mecânica de OAuth/resource-metadata, fica naturalmente ao lado das páginas de OAuth já existentes em vez de fragmentar a jornada de leitura em duas abas (descartada: Discovery como aba própria — mais destaque, mas fragmenta a leitura).
- Estilo de referência MCP (Overview/Key Details/Learn More): porque o protocolo é construído explicitamente sobre MCP, e a pesquisa trouxe a estrutura real e verificada do site oficial do MCP como referência direta (descartadas: estilo RFC numerado tipo "memo"; estilo API docs comercial tipo Stripe).
- "Início" fundido em "Especificação": porque o estilo MCP oficial usa a própria página de overview como "home" da documentação, sem uma página de boas-vindas separada antes do overview — fundir evita duplicar propósito entre duas abas (descartada: manter "Início" simples + "Especificação" separada).
- Cadência de validação `per-step`: porque a migração da branch `gh-pages` tem risco real de repetir o incidente anterior do CNAME — validar passo a passo pega qualquer problema antes de acumular (descartadas: bundle, final, none).

## Assumptions
- Assume-se que não há consumidores externos com links profundos (deep links/anchors) já publicados apontando pras seções de discovery que serão removidas de `oauth-requirements.md`/`mcp-oauth.md` — o site é novo (v1 é o primeiro lançamento formal). Se errado: um consumidor externo perde o anchor específico, mas a página de destino (`oauth-requirements.md`/`mcp-oauth.md`) continua existindo e linkando pra `discovery.md`, então o pior caso é uma navegação extra, não um link morto.
- Assume-se que o `mike` não escreve um `.nojekyll` próprio na raiz da branch de forma que entraria em conflito com o `.nojekyll` já preservado na limpeza do step-2 — não há confirmação direta disso na documentação pesquisada, por isso o plano preserva explicitamente o `.nojekyll` já existente em vez de depender do `mike` recriá-lo. Se errado: o `.nojekyll` existente continua funcionando (preservá-lo é estritamente seguro, só seria redundante caso o `mike` também escreva o seu).
- Assume-se que o git do operador que vai rodar o primeiro `mike deploy` manual (step-2.2) já tem `user.name`/`user.email` configurados globalmente (diferente do CI, que precisa configurar explicitamente) — não foi verificado via scout/worker. Se errado: o comando `mike deploy` falha ao tentar comitar, e o operador precisa rodar `git config user.name`/`user.email` antes de repetir o comando.
