    OAuth Flow¶

    This section documents the authentication and authorization flow used to connect a Partner (restaurant software) to the Platform and allow secure access to data via MCP.

    Participants¶

    Participant Description
    User Person who operates the platform and connects the partner
    Platform Agent that consumes the data via MCP
    Login (Partner) Login page of the restaurant software
    OAuth (Partner) Partner's authorization server
    MCP Ecosystem MCP server that exposes the tools
    DataBridge (Partner) Partner's data access layer (runs the queries)

    Partner

    "Partner" represents any integrated restaurant software. DataBridge is a partner-side component, not a platform component.

    How the platform obtains OAuth before the flow¶

    Before the authorization flow, the platform needs to discover the authorization server endpoints and the client credentials. There are three scenarios:

    • No discovery metadata → manual configuration: the partner provides the endpoints and credentials (client_id/client_secret) explicitly.
    • With metadata + DCR → automatic flow: the platform reads the metadata (RFC 8414) and self-registers as a client (RFC 7591). Nothing is exchanged manually.
    • With metadata, without DCR → automatic endpoint discovery, but the credentials (client_id/client_secret) are provided manually.

    Info

    The authorization server requirements are the same in all scenarios. See OAuth Requirements for the full breakdown.

    Flow steps¶

    1. Partner connection¶

    1. User → Platform: clicks "Connect Partner".
    2. Platform → Login: redirects the user sending client_id, scopes and the PKCE flow parameters.
    3. User → Login: enters credentials (email/password) and performs MFA if necessary.
    4. Login → OAuth: validates the provided credentials.
    5. OAuth → Platform: returns an authorization code via callback.
    6. Platform → OAuth: exchanges the authorization code for tokens using the PKCE code_verifier.
    7. OAuth → Platform: returns access_token (JWT) and refresh_token.
    8. Platform: stores the connection tokens with the partner.
    9. Platform → User: informs that the partner was connected.

    2. Query about partner data¶

    1. User → Platform: sends a prompt involving partner data.
    2. Platform → MCP: runs a tool — in the example, listar_lojas — with Bearer JWT.
    3. MCP: validates the JWT (signature, iss, aud, exp).
    4. MCP → OAuth (Partner): calls GET /userinfo with the Bearer token to obtain the user's authorization context (identity + permissions).
    5. OAuth (Partner) → MCP: returns sub, email and profile_permissions.
    6. MCP: applies the authorization logic — determines which merchants/resources the user can access.
    7. MCP → Platform: returns the list of authorized merchants.

    3. Data query¶

    1. Platform → MCP: runs tool_call buscar_dados(merchant_ids) with Bearer JWT.
    2. MCP: validates the JWT (signature, iss, aud, exp) and checks the user's authorization scope.
    3. MCP → DataBridge (Partner): runs the necessary queries against the partner's data store, filtered by the authorized merchant_ids.
    4. DataBridge → MCP: returns the requested data.
    5. MCP → Platform: returns the result of the tool execution.
    6. Platform → User: displays the response with the merchant data.
